# PC Monitoring Agent

## Overview

The goal of this project is to develop a lightweight Windows monitoring agent that runs silently in the background and reports important system health information through a Telegram bot.

The application should:

- Continuously monitor a small set of system metrics.
- Send alerts only when user-defined thresholds are exceeded.
- Respond to Telegram commands for on-demand status.
- Be modular and easy to extend in the future.

Python is chosen as the implementation language due to its excellent Windows support, availability of hardware monitoring libraries, and mature Telegram bot ecosystem.

---

# Architecture

```
Windows Startup
        │
        ▼
 Task Scheduler
        │
        ▼
MonitorAgent.exe
        │
        ├── Config Manager
        ├── Idle Monitor
        ├── Temperature Monitor
        ├── RAM Monitor
        ├── Telegram Bot
        └── Logger
```

The application will run continuously in the background with a configurable polling interval (default: 30 seconds).

---

# Telegram Integration

Telegram will be used instead of WhatsApp because it provides a free and officially supported Bot API that can both send notifications and receive commands over simple HTTP requests. The Bot API supports sending messages (`sendMessage`) and receiving commands via long polling or webhooks, making it well suited for a lightweight monitoring agent. :contentReference[oaicite:0]{index=0}

The bot will serve two purposes:

- Push important alerts
- Respond to user commands

# Metrics to Monitor

Only important metrics will be monitored.

## CPU Temperature

Monitor:

- Current CPU package temperature

Alert when:

```
CPU Temperature > Config Threshold
```

Example:

```
🔥 CPU Temperature Alert

Current:
92°C

Threshold:
90°C
```

---

## GPU Temperature

Monitor:

- Current GPU Core temperature

Alert when:

```
GPU Temperature > Config Threshold
```

Example:

```
🔥 GPU Temperature Alert

Current:
84°C

Threshold:
80°C
```

---

## RAM Usage

Monitor:

- Percentage of RAM currently in use

This value will **not** trigger alerts initially.

It is intended for status reporting only.

Example:

```
RAM Usage

43%
```

---

## Idle Time

Determine how long Windows has been idle by measuring the time since the last keyboard or mouse input.

Alert when:

```
Idle Time > Config Threshold
```

Example:

```
⚠️ Idle Alert

No keyboard or mouse input

Duration:
4h 18m
```

---

# Telegram Commands

## /status

Returns the current health of the monitored node.

Example response:

```
🖥 Node Status

CPU Temp : 54°C
GPU Temp : 47°C
RAM Usage: 39%
Idle Time: 12 minutes

Status:
Healthy
```

No alerts are generated by `/status`; it is purely informational.

---

# Alert Behaviour

Alerts should only be sent when thresholds are crossed.

Example:

```
CPU
89°C
↓

91°C

↓

Send Alert

↓

Remain above threshold

↓

Do Nothing

↓

Drops to 72°C

↓

Reset Alert State

↓

91°C again

↓

Send Alert
```

This prevents notification spam.

The same behaviour applies to:

- CPU temperature
- GPU temperature
- Idle time

---

# Configuration

All thresholds should be configurable without modifying code.

Example:

```yaml
poll_interval_seconds: 30

idle:
  threshold_minutes: 240

cpu:
  max_temp: 90

gpu:
  max_temp: 80
```

---

# Startup

The monitoring agent should start automatically when Windows boots.

Preferred approach:

- Windows Task Scheduler

Advantages:

- Starts automatically
- Runs in the background
- Can restart after failure
- Does not rely on Explorer or the Startup folder

---

# Logging

A daily log file should be maintained for diagnostics. Defaulted to off. Can be toggled on when needed for debugging.

Example:

```
2026-07-07.log
09:15 Agent started
09:15 CPU 47°C
09:15 GPU 42°C
13:22 Idle alert sent
18:04 CPU alert sent
```

# Future Expansion

The architecture should remain modular so that additional monitors can be added without modifying the application's core.

Potential future modules include:

- Disk usage
- Disk temperature
- Internet connectivity
- Sunshine status
- Moonlight connection status
- Steam status
- Windows Update status
- UPS battery monitoring
- Process monitoring

Each monitor should implement a common interface, allowing the main application loop to remain unchanged when new modules are introduced.
